\subsection{Architektur-Übersicht}
\label{sub:architektur_uebersicht}
\textbf{Gesamtarchitektur}:
Das System folgt einer Microservice-Architektur. Jeder Use Case (UC) wird als eigenständiger Service umgesetzt. Dadurch erhalten die einzelnen UCs getrennte Lebenszyklen, unabhängige Deployments und eine klare fachliche Verantwortlichkeit. Zusätzlich wird eine Isolation auf Prozessebene erreicht, sodass Fehler oder Abstürze eines Services keine Auswirkungen auf andere UCs haben.

Insbesondere im Kontext von Fully Homomorphic Encryption (FHE) ist diese Trennung vorteilhaft, da jeder Service seinen eigenen ServerKey im Arbeitsspeicher hält. In einer monolithischen Architektur würden sich die Speicheranforderungen aller UCs gegenseitig beeinflussen.

Die Services sind als Rust-Anwendungen implementiert und verwenden das Framework Axum für die Bereitstellung von HTTP-APIs. Wiederkehrende Funktionalitäten wie Health-Endpunkte, Prometheus-Metriken, Tracing und OpenAPI-Dokumentation werden über gemeinsame Shared Crates bereitgestellt.

Die Architektur besteht aus folgenden Hauptkomponenten:

\subsection{Build, Deployment, Tests}
\label{sub:build_deployment_tests}
\textbf{Build-Pipeline}:
Das Projekt wird als Cargo-Workspace und Monorepo organisiert.

Für die Containerisierung wird ein eigenes Docker-Image pro UC-Service verwendet. Die Images werden mittels Multi-Stage-Builds und cargo-chef erzeugt, um Abhängigkeiten zwischenzuspeichern und Buildzeiten zu reduzieren.

Zur Optimierung der FHE-Leistung wird die tfhe-Crate bereits im Entwicklungsprofil mit opt-level=3 kompiliert.

Für produktive Builds wird zusätzlich eine CPU-Optimierung über target-cpu=znver5 genutzt.

\textbf{CI/CD}:
Die CI/CD-Pipeline basiert auf GitHub Actions.

Wesentliche Bestandteile:
\begin{itemize}
    \item Pfadbasierte Change Detection mittels dorny/paths-filter
    \item Clippy als verpflichtendes Qualitäts-Gate (-D warnings)
    \item Automatischer Patch-Version-Bump nach Merge auf main
    \item Veröffentlichung der Container-Images in GHCR
    \item Automatische Aktualisierung der Helm-Konfiguration
    \item Deployment über ArgoCD nach dem GitOps-Prinzip
\end{itemize}

\textbf{Deployment}:
Das Deployment erfolgt auf einem k3s-Cluster.

Verwendete Infrastrukturkomponenten:
\begin{itemize}
    \item Traefik (Gateway)
    \item ArgoCD (GitOps)
    \item KEDA (Scale-to-Zero)
    \item Redis
    \item Prometheus
    \item Grafana
    \item Tempo
\end{itemize}

Helm-Charts werden zur Verwaltung aller Kubernetes-Ressourcen verwendet.

\textbf{Teststrategie}:
Die Teststrategie umfasst:
\begin{itemize}
    \item Unit-Tests: Tests einzelner Komponenten und Funktionen innerhalb der Services.
    \item Integrationstests: Tests der Endpunkte und des Zusammenspiels mehrerer Komponenten. Die Integrationstests werden im Release-Modus ausgeführt, um realistische Laufzeiten für FHE-Operationen zu gewährleisten.
    \item FHE-Korrektheitstests: FHE-Ergebnisse werden gegen Klartextreferenzen validiert.
\end{itemize}

\textbf{Testausführung}:
\begin{itemize}
    \item \verb|cargo nextest| als Test-Runner
    \item \verb|cargo llvm-cov| zur Ermittlung der Testabdeckung
    \item Ausführung mit \verb|--test-threads=1|, um Speicherprobleme durch parallele ServerKey-Dekompression zu vermeiden
\end{itemize}

\textbf{Testabdeckung}:
Die Testabdeckung wird über \verb|cargo llvm-cov| ermittelt.

\textbf{Hinzufügen eines neuen Services}:
\begin{enumerate}
    \item Neuer Rust-Service als Crate im Cargo-Workspace anlegen.
    \item Shared Crates als Dependencies einbinden.
    \item Dockerfile und Helm-Chart ergänzen.
    \item Routing-Konfiguration im Gateway erweitern.
    \item GitHub-Action-Pipeline aktualisieren.
    \item Deployment über ArgoCD automatisch ausrollen.
\end{enumerate}
