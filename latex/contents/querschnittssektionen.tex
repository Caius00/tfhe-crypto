\textbf{Verwendete Patterns}:
\begin{itemize}
    \item \textbf{Mono-Repo}: Der gesamte Code (Rust-Services, Shared Crates, Angular-Frontend, Helm-Charts, CI-Workflows, Dokumentation) liegt in einem einzigen Git-Repo. Das erlaubt atomare Commits über mehrere Schichten hinweg und vermeidet Versions-Mismatches mehrerer Repos.
    \item \textbf{Microservice-Pattern}: Jeder Use Case ist ein eigener Service mit eigenem Lebenszyklus, eigenem Namespace und gegebenenfalls eigener Datenbank.
    \item \textbf{Cargo Workspace}: Ein einziges Cargo-Projekt enthält alle Services und geteilten Bausteine als Sub-Crates. Vorteil ist eine gemeinsame Cargo.lock, ein einzelner \verb|cargo build|-Aufruf kompiliert alles und Versionen sind zentral pinnbar.
    \item \textbf{Shared Library}: Wiederkehrende Aufgaben wie Health, Metriken, Tracing und OpenAPI-Doku liegen in \verb|shared/|-Crates und werden per Pfad-Dependency in jeden Service eingehängt.
    \item \textbf{Code-First OpenAPI}: Die OpenAPI-Spec wird nicht handgeschrieben, sondern zur Laufzeit aus den Rust-Typen generiert (via \verb|aide| und \verb|schemars|). DTOs im Code sind die Quelle der Wahrheit, Swagger-UI und JSON-Spec entstehen automatisch.
    \item \textbf{Stateless-by-Default mit optionalem In-Memory-State}: Die meisten Services sind zustandslos. Wo ein UC eine Session braucht, lebt der State im RAM des Pods, nicht in der Datenbank, weil dort niemals Schlüssel oder noch-entschlüsselbare Ciphertexte liegen dürfen.
    \item \textbf{Path-based Routing}: Services kennen ihren öffentlichen Pfad nicht. Das Routing wird komplett am Gateway gemacht.
\end{itemize}

\subsection{Gateway und Routing}
\label{sub:gateway_und_routing}
Im Cluster läuft nur Traefik als öffentliche Eintrittstür. Er nimmt HTTP auf Port 80 entgegen und entscheidet anhand des Pfads, an welchen Service der Request weitergeht (z. B. /leaderboard/... $\rightarrow$ Leaderboard-Service). Für die Datenbank-Zugriffe von außen (Service 1 Redis, Service 6 Postgres) kommen TCP-Listener auf Port 6301 bzw. 5432 dazu.

\textbf{Was Traefik mit einem Request macht} (z. B. GET /leaderboard/123/entries):
\begin{enumerate}
    \item Schaut auf den Pfad-Präfix - passt zur HTTPRoute des Leaderboard-Services.
    \item Strippt den Präfix weg, der Service empfängt nur noch /123/entries. Dadurch wissen die Services nichts von ihrem öffentlichen Pfad - das macht sie umzieh-bar.
    \item Setzt einen internen Host-Header, damit der nachgeschaltete KEDA-Interceptor (siehe unten) weiß, welcher Service gemeint ist.
    \item Leitet den Request weiter - nicht direkt an den Service-Pod, sondern erst an den Interceptor.
\end{enumerate}

\textbf{Was Traefik sieht}: 
HTTP-Methode, Pfad, Header, Body - den Body aber nur als Byte-Strom, ohne ihn zu lesen oder zu verändern. Keine Authentifizierung, kein Rate-Limit, keine WAF - jeder, der die URL kennt, kann beliebige Requests an jeden Service schicken.

Kurze Begriffsklärung dazu:
\begin{itemize}
    \item WAF (Web Application Firewall) - Filter, der HTTP-Requests auf bekannte Angriffsmuster (SQL-Injection, XSS, Path-Traversal, …) prüft und blockiert.
    \item OIDC (OpenID Connect) - Standard für Authentifizierung über einen externen Identity-Provider (Google, GitHub, Keycloak, …). Der Nutzer loggt sich beim Provider ein, der stellt ein signiertes Token aus, das die Anwendung dann prüft.
\end{itemize}
Das ist im Rahmen eines Uni-Projekts bewusst so akzeptiert: das System ist kein Produkt, sondern eine Lernumgebung für FHE. Für einen Produktiv-Betrieb müsste ein Auth-Layer (OIDC am Gateway oder Token-Prüfung pro Service) und ein Rate-Limit ergänzt werden.

\textbf{Fehler}: 5xx-Antworten der Services werden 1:1 durchgereicht. Wenn ein Service gerade hochfährt, sieht der Client kein 503 - der Interceptor puffert solange (s. nächster Abschnitt). Erst wenn der Hochfahr-Vorgang in den Timeout läuft (30 s), gibt es ein 504 Gateway Timeout.

\subsection{Key Lifecycle}
\label{sub:key_lifecycle}
Aus Sicht der Schlüssel gibt es genau zwei Rollen:
\begin{itemize}
    \item Initiator - eine Partei mit dem ClientKey. Erstellt die Session, kann entschlüsseln.
    \item Teilnehmer - null bis beliebig viele weitere Parteien mit nur dem PublicKey. Können verschlüsseln, aber nicht entschlüsseln.
\end{itemize}

Wer in welcher Rolle ist, hängt vom jeweiligen UC ab und steht in dessen Sektion - manche UCs kommen mit nur einer Partei (Initiator allein) aus, andere lassen viele Teilnehmer zu.

In TFHE gibt es drei Arten von Schlüsseln, die der Initiator erzeugt:
\begin{itemize}
    \item ClientKey - der private Schlüssel zum Entschlüsseln. Bleibt immer beim Browser und wird nie an einen Server geschickt.
    \item ServerKey - erlaubt dem Server, auf verschlüsselten Daten zu rechnen, ohne sie selbst entschlüsseln zu können. Wird beim Erstellen der Session hochgeladen.
    \item PublicKey - kann an Teilnehmer weitergegeben werden, damit sie verschlüsseln können, ohne den ClientKey zu kennen. Wenn ein UC keine Teilnehmer hat, bleibt der PublicKey ungenutzt.
\end{itemize}
Konzeptueller Datenfluss (Details, Endpunkt-Namen und ob es überhaupt einen Session-Begriff gibt, hängen vom UC ab):
\begin{enumerate}
    \item Schlüsselerzeugung - der Initiator erzeugt client-seitig alle drei Schlüssel. Der ClientKey verlässt den Client nie.
    \item ServerKey-Übertragung - der Initiator schickt den ServerKey zum Service.
    \item Dekompression - der Service dekomprimiert den ServerKey. Da das mehrere Sekunden CPU-Zeit und mehrere hundert MB RAM kostet, läuft es in einem Hintergrund-Thread und nicht im HTTP-Handler.
    \item Eingaben - werden verschlüsselt an den Service geschickt (vom Initiator selbst mit ClientKey oder PublicKey, oder von Teilnehmern mit dem PublicKey).
    \item Berechnung - der Service rechnet auf den verschlüsselten Werten.
    \item Ergebnis - kommt verschlüsselt zurück. Nur der Initiator kann es mit seinem ClientKey entschlüsseln.
\end{enumerate}
\textbf{Lebensdauer}: 
Schlüssel und sonstiger Sitzungs-State leben ausschließlich im RAM des Service-Pods. Auf der Festplatte oder in einer Datenbank landen nur fachliche Klartext-Metadaten, niemals Schlüssel oder Ciphertexte, die noch jemand entschlüsseln könnte. Wenn der Pod neu startet oder von KEDA auf 0 skaliert wird, ist alles im RAM weg - die betroffene Partei muss von vorn anfangen. Einige UCs ergänzen das um zusätzliche Aufräum-Mechanismen (z. B. Idle-Eviction einzelner Sessions).

\label{sub:gateway_und_routing}

Im Cluster läuft nur Traefik als öffentliche Eintrittstür. Er nimmt HTTP auf Port 80 entgegen und entscheidet anhand des Pfads, an welchen Service der Request weitergeht. Für die Datenbank-Zugriffe von außen (Service 1 Redis, Service 6 Postgres) kommen TCP-Listener auf Port 6301 beziehungsweise 5432 dazu. Diese externen Datenbankzugriffe werden über die Gateway API im Experimental Channel in Version 1.2.0 abgebildet, weil das nötige TCPRoute im Standard-Channel noch nicht enthalten ist.

\textbf{Verarbeitung eines Requests}:
Am Beispiel eines Aufrufs \verb|GET /leaderboard/123/entries| arbeitet Traefik in folgenden Schritten:

\begin{enumerate}
    \item Der Pfad-Präfix wird ausgewertet. Im Beispiel passt der Präfix zur HTTPRoute des Leaderboard-Services.
    \item Traefik strippt den Präfix weg. Der Service empfängt nur noch \verb|/123/entries|. Dadurch wissen die Services nichts von ihrem öffentlichen Pfad und bleiben umziehbar.
    \item Ein interner Host-Header wird gesetzt, damit der nachgeschaltete KEDA-Interceptor weiß, welcher Service gemeint ist.
    \item Der Request wird weitergeleitet, allerdings nicht direkt an den Service-Pod, sondern erst an den Interceptor.
\end{enumerate}

\textbf{Sichtbarkeit von Daten im Gateway}:
Was Traefik sieht, sind HTTP-Methode, Pfad, Header und der Body. Den Body sieht es nur als Byte-Strom, ohne ihn zu lesen oder zu verändern. Da der Body bei FHE-Endpunkten nur Base64-kodierte Ciphertexte enthält, bleibt der eigentliche Inhalt für das Gateway opak.

\textbf{Authentifizierung und Rate Limiting}:
Es gibt aktuell keine Authentifizierung, kein Rate-Limit und keine Web Application Firewall am Gateway. Jeder, der die URL kennt, kann beliebige Requests an jeden Service schicken. Das ist im Rahmen eines Uni-Projekts bewusst so akzeptiert. Das System ist kein Produkt, sondern eine Lernumgebung für FHE. Für einen Produktiv-Betrieb müsste ein Auth-Layer (etwa OIDC am Gateway oder Token-Prüfung pro Service) und ein Rate-Limit ergänzt werden.

\textbf{Fehlerpropagation}:
5xx-Antworten der Services werden 1:1 durchgereicht. Wenn ein Service gerade hochfährt, sieht der Client kein 503, weil der KEDA-Interceptor den Request solange puffert. Erst wenn der Hochfahr-Vorgang in den Timeout von 30 Sekunden läuft, antwortet das Gateway mit 504 Gateway Timeout.

\textbf{Body-Limit}:
Die Größen sind insbesondere für die Endpunkte relevant, die einen ServerKey entgegennehmen. Axum cappt den Body sonst standardmäßig bei 2 MB. In den Services ist deshalb explizit ein Limit von 2 GiB gesetzt, damit der Upload des dekomprimierbaren ServerKey-Materials durchgeht.

\subsection{Build, Deployment, Tests}
\label{sub:build_deployment_tests}

\textbf{Pipelines}:
Die CI/CD-Pipelines liegen unter \verb|.github/workflows/| und laufen vollständig auf GitHub-hosted Runnern (\verb|ubuntu-latest|). Auf dem Cluster selbst gibt es keine self-hosted Runner.

\begin{tabular}{||l|p{3cm}|p{6cm}||}
    \hline
    \textbf{Workflow} & \textbf{Wann} & \textbf{Was} \\
    \hline\hline
    ci.yml & Push auf Feature-Branch & Format-Check, Linter (Clippy als verpflichtendes Gate mit \verb|-D warnings|), Tests mit Coverage \\
    \hline
    release.yml & Push auf main & Patch-Version bumpen, Docker-Image bauen und nach ghcr.io pushen, README und Helm-Values updaten \\
    \hline
\end{tabular}

Der Helm-Values-Update am Ende ist wichtig. Erst wenn das Image garantiert in der Registry liegt, wird der Tag im Chart hochgezogen. Sonst würde ArgoCD versuchen, ein noch nicht existierendes Image zu deployen.

\textbf{Image-Build}:
Das Dockerfile ist als Multi-Stage-Build mit \verb|cargo-chef| umgesetzt. \verb|cargo-chef| ist ein Trick, der Rust-Dependencies separat von der eigenen Quellcode-Schicht baut. Bei Code-Änderungen ohne neue Dependency wird der teure Compile-Schritt aus dem Docker-Cache wiederverwendet. Builds gehen von rund 10 Minuten auf etwa 1 Minute runter. Das fertige Image basiert auf \verb|debian:bookworm-slim| und ist 100 bis 200 MB groß. Zur Optimierung der FHE-Leistung wird die \verb|tfhe|-Crate bereits im Entwicklungsprofil mit \verb|opt-level=3| kompiliert. Für produktive Builds kommt zusätzlich eine CPU-Optimierung über \verb|target-cpu=znver5| zum Einsatz.

\textbf{Deployment}:
Das Deployment erfolgt auf einem k3s-Cluster nach dem GitOps-Prinzip mit ArgoCD. Jede Änderung an \verb|helm/services/*| wird gepusht, ArgoCD erkennt sie und deployt automatisch ohne manuelles \verb|helm install|. Die Infrastruktur-Charts (Traefik, ArgoCD, KEDA, Monitoring) werden bewusst nicht über ArgoCD verwaltet, sondern manuell per \verb|helm install| installiert, damit beim Neuaufbau des Clusters eine klare Reihenfolge eingehalten werden kann.

\textbf{Teststrategie}:
Jeder Service bringt seine eigenen Tests mit. Was konkret geprüft wird, hängt von der Fachlichkeit des UCs ab und steht in der jeweiligen UC-Sektion. Auf Pipeline-Ebene ruft die CI für jeden Service einheitlich \verb|cargo test --release -- --test-threads=1| auf.

\begin{itemize}
    \item \textbf{Unit-Tests}: Tests einzelner Komponenten und Funktionen innerhalb der Services.
    \item \textbf{Integrationstests}: Tests der Endpunkte und des Zusammenspiels mehrerer Komponenten. Sie laufen im Release-Modus, um realistische Laufzeiten für FHE-Operationen zu gewährleisten.
    \item \textbf{FHE-Korrektheitstests}: FHE-Ergebnisse werden gegen Klartextreferenzen validiert.
\end{itemize}

Das Flag \verb|--release| ist Pflicht, weil FHE im Debug-Modus rund 10-mal langsamer ist. \verb|--test-threads=1| verhindert, dass parallele Tests den ServerKey-Speicher mehrfach allokieren.

\textbf{Testabdeckung}:
Die Code Coverage wird in der CI per \verb|cargo-llvm-cov| pro Service ermittelt und als Zeilen-Coverage-Badge ins jeweilige Service-README geschrieben. Sie ist nicht hart als CI-Gate erzwungen. Der Wert dient als Indikator, nicht als Block.

\textbf{Hinzufügen eines neuen Services}:
\begin{enumerate}
    \item Neuer Rust-Service als Crate im Cargo-Workspace anlegen.
    \item Shared Crates (health, metrics, observability, openapi-docs) als Dependencies einbinden.
    \item Dockerfile und Helm-Chart unter \verb|helm/services/| ergänzen.
    \item Routing-Konfiguration im Gateway um eine HTTPRoute mit passendem Pfad-Präfix erweitern.
    \item GitHub-Actions-Pipeline auf den neuen Service ausweiten.
    \item Deployment über ArgoCD automatisch ausrollen lassen.
\end{enumerate}
